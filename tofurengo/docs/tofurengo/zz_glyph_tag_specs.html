Glyph Tag Specification (仕様書)

Author: jp-rad
Established: 2026‑10‑02 (つるつる豆腐の日)
Last Updated: 2026‑10‑02

1. 適用範囲および目的（Scope and Purpose）

本仕様書は、文字図形識別名（glyph-name）を基軸として字形情報を抽象化・表現するための共通タグ形式「Glyph Tag」の構文および処理モデルを規定します。

1.1 背景と目的（Background and Purpose）

デジタル環境における未定義グリフの代替表示（いわゆる「豆腐文字」）の発生、および既存システム等に閉じた特定の字形構造は、文字情報の厳密性と相互運用性を著しく損なう長年の構造的課題です。
また、異体字を含む人名等の検索においては、実装文字コード（IVS等）を正確に入力して検索することが困難であり、検索性の低下を招く要因となっています。

本仕様書は、制定日（2026-10-02）を象徴的な基点とし、文字図形識別名（glyph-name）を軸とする抽象化層を確立することを目指します。

これにより、表示基盤に依存する豆腐文字の発生を根絶するとともに、標準・非標準を問わず多様な字形体系を包摂・保全し、いかなる環境においても意図された字形の正確かつ堅牢な描画を実現します。
さらに、基本文字コードを用いた共通展開モデルを提供することで、一般的な日本語入力環境からでも人名等の高度な検索・照合を容易にします。

1.2 コンセプト：処理系と人間系の両立

Glyph Tag は、「処理系（プログラム・表示システム）も人間系（開発者・運用者）も直感的に理解できる」 構造を目指して設計されています。

  • 人間系への可読性: 構造がシンプルで視認しやすく、ソースコードやテキストデータとして直接読んだ際にも意図（文字図形名、代替コード、実装コード）が直感的に把握できます。
  • 処理系への明確性: 正規化（データ確定）と描画（表示展開）の責務を分離し、プログラム側で決定論的にパース・処理できる軽量な構文を提供します。

1.3 主な機能

  1. 抽象レイヤの提供: 文字図形識別名を「基本文字コード」および「実装文字コード」へ対応付けます。
  2. 共通フォーマットの標準化: MJ文字図形名やGJ文字図形名、および独自に定義された固有字形をはじめとする異なる字形体系を統一的に扱います。
  3. 固有文字体系の保全と吸収: 固有の表示環境が消失した場合でも、抽象タグとして字形識別情報および縮退表示用情報を保持・継承します。
  4. 検索性の飛躍的向上: 描画（基本優先モード）を用いて基本文字コードへ展開した文字列を事前に生成・保持しておくことで、特殊な異体字の入力を要しない一般的な入力環境からの容易な人名・住所等の検索を可能にします。
  5. 処理モデルの分離: 正規化（Normalization）フェーズと描画（Rendering）フェーズを明確に分離します。

2. 用語の定義（Terms and Definitions）

本仕様書において使用する主要な用語の定義は以下の通りです。

  • 文字図形識別名（glyph-name）: 特定の字形体系において文字図形（glyph）を一意に識別するための抽象的な名称（例: MJ文字図形名、GJ文字図形名、固有字形識別名）。
  • 基本文字コード（Basic Character Code）: Unicode 標準において異体字選択符号（IVS）等を含まない単一の標準コードポイント（b 属性）。未符号化字形等においては縮退表示用の代替文字を含みます。
  • 実装文字コード（Implementation Character Code）: 実装基盤において対象の字形を表示するために採用されるコードポイント並び（v 属性）。Unicode 標準文字のほか、IVS（Ideographic Variation Sequence）や PUP（Private Use Plane：私用面）等の固有コードを含みます。
  • 字形体系識別子（Glyph System Identifier）: 適用される字形データセットの体系を一意に識別するためのコード（set 属性）。
  • 表示システム: Glyph Tag を解釈・変換・表示するアプリケーション、オペレーティングシステム、およびフォント等で構成される処理基盤全般。
  • 豆腐文字（Tofu）: 適用可能なコードポイントが存在しない場合、または該当するグリフが描画できない場合に表示システムが出力する代替記号。

3. 構文仕様（Syntax Specification）

Glyph Tag の基本構文を以下に示します。

{<glyph-name> [b=<UCSSeq>] [v=<UCSSeq>] [set=<Identifier>]}

3.1 構成要素

  • <glyph-name>（必須）: 体系固有の文字図形識別名。
  • b=<UCSSeq>（任意）: 基本文字コード。
  • v=<UCSSeq>（任意）: 実装文字コード。
  • set=<Identifier>（任意）: データセット識別子。

3.2 属性の記述規則

  • 属性（b, v, set）の記述順序は任意です。
  • 指定の有無にかかわらず、各属性値は正規化処理によって自動的に決定・上書きされます。

3.3 UCSSeq（UCS コードポイント系列）の表現

UCSSeq は、1 つ以上の Unicode コードポイントを半角スペース区切りで並べた系列です。

U+XXXX
U+XXXX U+YYYY
U+XXXX U+YYYY U+ZZZZ

4. エスケープ処理規則（Escape Rules）

Glyph Tag の開始記号 { をそのまま地の文として表示したい場合は、{{ と記述します。

4.1 基本エスケープ規則

  • {{ として記述された要素は Glyph Tag 構造の解析（パース）対象から除外されます。
  • 閉じ記号 } に対するエスケープ規則は定義しません。 閉じ記号は常に地の文、またはタグ構造の終端として評価されます。

4.2 各処理フェーズにおけるライフサイクル

  1. 解析時: {{ は構文解析の対象外として保護・保持されます。
  2. 正規化フェーズ: {{ の表記形態をそのまま維持（保持）して出力します。
  3. 描画フェーズ: エスケープが解除され、単一の文字 { に変換されます。

4.3 評価例

例 1: { を通常の文字として出力する場合

  • 入力: 現在の表記は {{MJ022335} です。
  • 正規化結果: 現在の表記は {{MJ022335} です。
  • 描画結果: 現在の表記は {MJ022335} です。

例 2: タグの直後に閉じ波括弧が連続する場合（}}}） 最内方の {...} がタグとして認識され、後続する }} は地の文として評価されます。

  • 入力: タグ: {MJ022335}}}
  • 正規化結果: タグ: {MJ022335 b=U+845B v=U+845B U+E0102 set=mj}}}
  • 描画結果: タグ: 葛}}

5. 正規化処理（Normalization Process）

正規化フェーズは、Glyph Tag を適用環境の字形体系に従って再解釈し、属性値を確定・置換（上書き）する処理です。

5.1 正規化の目的

  • 文字図形識別名を適用環境の文字図形表（Glyph Table）と照合します。
  • タグ内の既存の属性値の有無にかかわらず、適用環境の定義に従って基本文字コード（b）および実装文字コード（v）を上書き決定します。
  • 字形体系識別子（set）を適用環境の識別子で置換・更新します。

5.2 処理手順

  1. エスケープ表記（{{）をタグ解析対象から除外・保護します。
  2. 対象文字列中の Glyph Tag（{...}）を抽出し、各要素に分解します。
  3. 文字図形識別名をデータセットと照合し、b, v, set の各属性値を適用環境の定義値で上書き・置換します。
  4. 保護していたエスケープ表記（{{）を保持したまま、正規化文字列を出力します。

6. 描画処理（Rendering Process）

描画フェーズは、正規化済みの Glyph Tag を表示対象の Unicode 文字列へ展開する処理です。

6.1 コードポイント選択規則

タグに付与されている属性から、表示に使用するコードポイントを以下の優先順位に従って決定します。

  • 実装優先モード（既定）: 実装文字コード（v） ➔ 基本文字コード（b） ➔ 豆腐文字
  • 基本優先モード: 基本文字コード（b） ➔ 豆腐文字

6.2 豆腐文字（Tofu）の出力

適用可能な文字コード（v および b）がタグ内に存在しない場合、または定義されていない場合は、表示システムが規定する豆腐文字（例: U+25A1「□」）を出力します。

6.3 エスケープの解除

描画処理の最終段階において、保持されていたエスケープ表記（{{）を解除し、文字（{）として出力します。

Annex（補足資料）

Annex A — Unicode IVS / IVD との整合性（国際標準）

  • IVS（Ideographic Variation Sequence）は ISO/IEC 10646 に規定されています。
  • IVD（Ideographic Variation Database）は Unicode Consortium が管理する異体字データベースです。
  • Moji_Joho IVD Collection は、日本の文字情報基盤（MJ文字）に基づき Unicode IVD に登録された公式コレクションです。
  • Glyph Tag の b/v 二層モデルは、IVD の基本文字＋異体字選択符号モデルと完全に整合します。

Annex B — MJ文字（Moji_Joho IVD）の定義例

MJ文字は Unicode に符号化済みであり、必要に応じて IVS を保持します。

MJ022335: { b: "U+845B", v: "U+845B U+E0102" }  // 奈良県葛城市の「葛」
MJ022336: { b: "U+845B", v: "U+845B U+E0103" }  // 東京都葛飾区の「葛」

Annex C — 行政事務標準文字（MJ＋GJ）の構成

行政事務標準文字は以下の要素で構成されます。

  • MJ文字: Unicode 符号化済み文字
  • GJ文字: Unicode 未符号化文字（PUP にて対応）

Annex D — GJ文字の表現手法（暫定私用面）

Unicode 未符号化である GJ文字は、Glyph Tag において以下の属性構造で表現します。

  • b（GJ代替文字 / fallback glyph）: 意味的・字形的に近い既存の UCS 文字または縮退代替文字を設定。
  • v（GJ暫定私用コード / PUP）: 実装基盤における私用面コードポイント（例: U+100ABC）を設定。

Annex E — フォント実装と参照情報

MJ文字およびGJ文字を実装した代表的なフォント環境と参照URLは以下の通りです。

DWPI明朝

DWPIex明朝

変体かな濁点等の IVS 割り当て実装フォント。

https://www.digitalwidearea.org/dwpi_mincho

Annex F — 既存・固有文字体系との連携モデル

Glyph Tag は既存システム等の固有文字体系との親和性を確保します。

  • 固有字形 ➔ 文字図形識別名（MJ文字図形名、GJ文字図形名、独自字形識別名等）へ割り当て
  • 字形データ ➔ b（標準文字コード/縮退代替コード）および v（実装コード/私用面コード等）にマッピング
  • フォント環境が変更・移動した場合でも、抽象タグとして字形識別情報および縮退表示用情報を保持可能
